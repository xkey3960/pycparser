# 设计文档-编译管线优化（QOL-4）

> 对应 TODO.txt `[QOL-4] 编译管线优化`（P5 远期，2026-08-22 用户提出）。
> 两个需求：① 多文件编译多线程加速；② AST 缓存持久化（按文件 hash 命中，
> 跳过重新编译 AST）。目标：不改变语义、不破坏既有测试与惰性/方案C/strict 模式。

---

## 一、现状

`CProgram.load()`（program.py:67）是唯一的解析入口：

```python
def load(self):
    for f in self.files:
        ast = parse_file(f, use_cpp=True, cpp_path=self.cpp_path,
                         cpp_args=self.cpp_args, parser=self.parser,
                         encoding=self.encoding)
        self.asts.append(ast)
    if self.lazy:
        g_source_index.build(self.asts, self.files)
        ...
```

每次运行都做：**gcc 预处理（子进程）+ pycparser 解析（GnuCParser）+ AST 构建**。
同一组文件反复编译（开发迭代、CI、测试）成本固定，无任何复用。

### 实测（同机）

| 场景 | 耗时 |
|------|------|
| 单文件解析（lib.c） | ~40ms |
| 串行解析 6 文件 | 223ms |
| **并行解析 6 文件**（ThreadPool 6） | **47ms（-79%）** |
| AST pickle round-trip | 通过（FileAST 可序列化/反序列化，同构） |

### 关键事实

1. `parse_file` 只做：调 gcc 预处理（子进程）+ 构建**独立** AST——无共享
   可变状态，**线程安全**（实测并行结果正确）。
2. pycparser AST（FileAST/ext 树）**可 pickle**（实测 round-trip 同构），
   支持磁盘持久化。
3. 后续阶段（sources 索引、typesys 注册、activate/link）**依赖共享全局
   状态**，必须保持串行。

## 二、设计

### 总体架构：load() 拆为"编译阶段（可并行/可缓存）+ 索引阶段（串行）"

```
load()
 ├─ ① 编译阶段（每个文件独立）：
 │     先查 AST 缓存（hash 命中 → 反序列化）
 │     未命中 → 并行 parse_file（线程池）
 │     结果按顺序收集到 self.asts
 └─ ② 索引阶段（串行，现状不变）：
     lazy → g_source_index.build(...)
```

### A. 多线程并行解析

- **时机**：只并行"预处理+解析"（无共享写）；索引/注册仍串行（sources.build、
  activate、link 全不动）。
- **实现**：`concurrent.futures.ThreadPoolExecutor`，max_workers 默认
  `min(os.cpu_count(), len(files))`；结果按输入顺序收集（`map` 保序）。
- **parser 实例**：每个线程创建自己的 GnuCParser（parser 有解析状态，
  不共享）；CProgram.parser 作为模板/工厂来源。
- **失败语义**：任一文件解析失败 → 整体 load 抛错（与串行一致，报错信息
  含文件路径）；用 `map` 在首错时取消其余任务。
- **开关**：`CProgram(..., parallel=True)` 默认开；`parallel=False` 退回串行
  （调试/单文件场景无线程开销）。

### B. AST 缓存持久化（文件 hash 命中）

- **缓存键**：`hashlib.sha256(文件内容 + cpp_args + parser 标识).hexdigest()`
  - 内容哈希：读源文件字节（预处理输出由 pycparser 内部做，但 gcc 预处理
    依赖文件内容与 -I 路径——缓存键必须含 cpp_args 与源码内容）。
  - parser 标识：`type(self.parser).__name__`（GnuCParser vs CParser 结果不同）。
- **缓存值**：pickle 序列化的 FileAST。
- **存储**：目录 `缓存根/.pycparser-ast-cache/<hash>.pkl`。
  - 缓存根默认：`<首文件所在目录>`（程序目录，符合"项目本地缓存"直觉）
    → 更稳妥：`~/.cache/pycparser/`（用户级，避免污染项目/云盘同步）。
    **采用用户级**：`os.path.expanduser('~/.cache/pycparser-ast/')`，
    可用环境变量 `PYCPARSER_AST_CACHE` 覆盖（含禁用：设空字符串）。
- **命中流程**：
  1. hash 文件存在 → pickle.load → FileAST（校验类型）
  2. 校验失败/版本不匹配 → 重新编译并覆盖
- **失效**：文件内容变化 → hash 不同 → 自然 miss；同名同内容 → 命中。
- **原子写**：写缓存先写临时文件再 rename（避免并发/中断产生半文件）。
- **开关**：`CProgram(..., ast_cache=True)` 默认开；`ast_cache=False` 关闭。

### C. 与既有模式的兼容性

| 模式 | 影响 |
|------|------|
| lazy 惰性 | load 后 build 索引用缓存的 AST——索引只扫 ext 名字，与来源无关 ✅ |
| link 全量 | asts 是反序列化对象，link 遍历/execute 照常 ✅ |
| 方案 C strict | run 走 reachable/activate，激活用 `_asts[path]`（缓存 AST）✅ |
| S4 static | activate/link 设 g_current_file=path，与 AST 来源无关 ✅ |
| L4 类型惰性 | ensure_complete 挂的是 AST 节点引用（_deferred），pickle 后引用完整 ✅ |
| 错误坐标 | AST 节点 coord 随 pickle 保留（coord 是字符串字段）✅ |
| 测试夹具 | 测试动态写文件（test 写 test/multi/*.c）→ 内容变化 hash 变 → miss 重编译 ✅ |
| 并发 | 缓存目录写用"临时文件+rename"原子化；多进程安全（不锁）✅ |

### 风险与对策

1. **pickle 兼容性**：pycparser/pycparserext 类路径 pickle 依赖模块导入。
   load 前已 import pycparser c_ast 与 GnuCParser → 反序列化环境一致。
   对策：pickle 时记录 `pickle 协议版本`，load 校验 `hasattr(ast, 'ext')`。
2. **缓存污染**：cpp_args 变化（-I 路径不同）→ hash 不同，天然隔离。
3. **线程 + 云盘**：源文件在云盘（华为云盘）读取无写锁问题；gcc 子进程
   并发调用由 OS 调度，实测无冲突。
4. **首次冷缓存**：第一次运行无缓存仍串行/并行编译；之后命中。

### 性能预期（实测数据支撑）

- 并行：6 文件 223ms → 47ms（**-79%**）；多核收益随文件数线性扩展。
- 缓存命中：跳过 gcc + 解析 → 单文件 ~40ms → **~2ms**（pickle load）；
  6 文件全命中 ≈ 十几 ms。
- 组合：二次运行（并行关闭亦可）近乎即时。

## 三、影响与验收

| 关注点 | 结论 |
|--------|------|
| 语义 | 编译阶段产物等价（同 AST 结构）；后续阶段零改动 |
